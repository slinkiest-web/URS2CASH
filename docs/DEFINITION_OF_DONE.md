## 2. Real bugs found and fixed this session

This was a verification pass, but the task's own HARD RULE — "for any failure, fix it and re-verify" — was exercised for real, twice.

### 2.1 A real regression: rating submission was silently broken since Prompt 19

**What was broken:** `prevent_profile_self_service_admin_fields()` (Prompt 19's self-service-lockdown trigger, built to stop a seller from directly PATCHing her own `is_admin`/`is_suspended`/etc.) blocks any `profiles` UPDATE where `auth.uid()` is non-null. `recompute_seller_rating` (Prompt 6) is a `SECURITY DEFINER` trigger that updates the *seller's* `profiles` row as a side effect of a `ratings` INSERT — and ratings are inserted through the **buyer's own authenticated session**, by deliberate design (Decision #76), not through service-role. `SECURITY DEFINER` elevates table privileges but does **not** change `auth.uid()`, which reads a connection-level GUC — so the cascading UPDATE still carried the buyer's own non-null `auth.uid()` and got blocked by the exact trigger meant to stop unrelated self-service tampering. **Every real rating submission since Prompt 19 shipped would have failed** the moment it tried to update the seller's denormalised rating average — a completely different, unrelated code path than the one Prompt 19 was protecting.

This was caught live by this session's own RLS verification script (a real buyer-session insert into `ratings` failing with the lockdown trigger's error message), not by inspection — the exact kind of bug a full-app verification pass exists to catch that a narrowly-scoped feature prompt cannot.

**The fix** (`supabase/migrations/20260804090000_fix_rating_trigger_regression.sql`): the lockdown trigger now also checks `pg_trigger_depth() <= 1` — true only for a *direct* top-level UPDATE, false when the UPDATE is cascading out of another trigger's own execution (which is exactly `recompute_seller_rating`'s situation, one level deeper). No client role can fake this signal (`authenticated`/`anon` cannot create triggers on `profiles` at all). Re-audited every other denormalised-counter trigger for the same class of bug: `increment_completed_sales_count`/`increment_dispute_upheld_count` both cascade from `orders`/`disputes`, neither of which has *any* authenticated UPDATE policy — every path to them is already service-role-only, so `auth.uid()` was already always null there, and they needed no change. `recompute_seller_rating` was the one and only case, because `ratings` is the one and only table with a direct (non-service-role) authenticated write path that cascades into another table's admin-protected columns.

**Re-verified after the fix:** all 34 checks in the definition-of-done RLS script pass, including the full ratings flow (insert succeeds, average recomputes correctly, a second rating on the same order fails at the real `23505` constraint) and every self-service-lockdown check that motivated the original trigger (an attacker still cannot self-grant `is_admin`, self-unsuspend, etc.).

### 2.2 A real, long-standing feature gap: sellers had no way to add a payout account

**What was missing:** §11.2's `resolveAndSavePayoutAccount(bankCode, accountNumber): Result<PayoutAccount>` and the `/api/paystack/resolve-account` route both existed only as a TODO comment and an empty placeholder directory since Prompt 1. `docs/PROJECT_STATUS.md` had correctly and consistently tracked this as "Not built" since the earliest reports — a known, deliberately-deferred gap, never assigned to a specific prompt — but DoD item 1 explicitly requires "resolves a bank account" as part of the signup-to-first-listing flow, which makes this gap a direct DoD failure, not just a nice-to-have.

**Built this session:**
- `src/lib/paystack/banks.ts` — a static list of 21 major Nigerian banks (traditional banks + the common fintechs: Kuda, OPay, PalmPay, Moniepoint). Every single code was checked against a real, live call to Paystack's own `/bank` endpoint before being committed — not typed from memory.
- `resolveBankAccount()` in `src/lib/paystack/index.ts` — calls Paystack's real `/bank/resolve` endpoint.
- `resolveAndSavePayoutAccount()` in `src/lib/actions/profile.ts` — matches the PRD's exact §11.2 signature. There is no code path anywhere that accepts an `accountName` parameter from the caller — the persisted name can only ever come from Paystack's own response, which is what actually makes §10 Epic A3 AC3's "fails if the account name is accepted as user input" impossible to violate, not just a UI convention.
- A `PayoutAccountForm` client component wired into the seller profile page: bank select + account-number input only (deliberately no account-name field to type into), a masked display of the saved account (last 4 digits only, AC6) once one exists, and a persistent (non-blocking) prompt when one doesn't (AC5).

**Live-verified against the real Paystack API** (not mocked): `resolveBankAccount("001", "0000000000")` — Paystack's own documented test bank/account combination — correctly resolves to `"TEST ACCOUNT 0000000000"`. Discovered along the way, and worth recording: Paystack's test-mode key allows only 3 real bank-resolve calls per day against real bank codes before returning a rate-limit message that itself names bank code `001` as the sanctioned unlimited test path — confirmed by hitting that exact limit live, then confirming `001` works without limit.

## 3. Additional checks from the task's own brief (beyond §13's literal text)

- **Disputes hold payouts and halt auto-transitions:** live-verified this session. A `shipped` order past its `auto_release_at` deadline is exactly the auto-release cron's own selection criterion (`status = 'shipped' AND auto_release_at <= now()`) — the moment a dispute is raised, `status` becomes `'disputed'`, which structurally no longer matches that query. Replayed the cron's exact query shape live against a real disputed order: zero rows returned. A `queued` payout is held (`status='held'`) the instant a dispute is raised (Prompt 17's own migration); this session additionally confirmed the deeper guarantee — a disputed-then-refunded order has **zero** payout rows at all, not a held one, because `release_order()` structurally cannot have created one before the dispute froze the order.
- **Admin actions re-verify role from the DB; a non-admin cannot reach an admin action even bypassing the UI:** live-verified this session by calling `admin_suspend_listing` directly via RPC as a real non-admin authenticated session — rejected outright (`EXECUTE` revoked at the database level, the same mechanism proven for every admin RPC since Prompt 19). `requireAdmin()`'s own DB re-query was re-confirmed correct for both a non-admin and a freshly-granted admin.
- **RLS tested with an authenticated non-owner client, every table:** 21 checks across all 11 tables this session (§1, DoD items 20 and throughout) — non-owner read/write rejected on `profiles`, `payout_accounts`, `listings`, `orders`, `payouts`, `order_status_transitions`; public-vs-private read boundaries confirmed correct on `categories`/`listings`/`ratings`; zero-policy deny-all confirmed on `moderation_flags`/`webhook_events`; buyer-only insert confirmed on `disputes`.

## 4. Lighthouse detail

Both runs used a real `next start` **production** build (not `next dev`), mobile form factor, simulated-3G throttling, and a genuinely-uploaded photo (fetched once and stored in the real local Supabase Storage bucket — not an external `picsum.photos` URL, which isn't in `next.config.ts`'s host allowlist and would have crashed `next/image` per the exact bug Decision #66 already documents).

| Page | Run 1 LCP | Run 2 LCP | Result |
|---|---|---|---|
| `/c/beauty` | 1.9s | — | **Pass**, comfortable margin |
| `/l/[id]` (real photo) | 3.3s | 2.9s | **Over target**, both runs |

The LCP element on the listing page was the `<h1>` title text, not the photo — Lighthouse's own breakdown attributes the overage almost entirely to "element render delay" (~2.0s) rather than resource download time (time-to-first-byte was a fast 307ms), which points at main-thread contention delaying paint commit rather than a slow network resource. `uptime` during the run showed a load average of 3.85–6.48 on this machine — the local Supabase Docker stack (11 containers) plus this session's own long history of processes were genuinely competing for CPU at measurement time, and Lighthouse's "simulate" throttling mode scales *real observed* main-thread timing from the trace, so real contention on the measuring machine directly inflates the reported number. No oversized page-specific bundle or render-blocking resource was found on inspection to explain the gap as an app-level defect (the large JS chunks present are Next.js/React framework baseline, not oversized page-specific code).

**This is reported as a flagged residual risk, not silently marked pass.** The responsible next step is re-measurement on an uncontended machine or, more decisively, a real Vercel preview deployment (which has a real CDN and no local Docker competing for CPU) — not further guessing in this sandboxed environment.

## 6. Residual risks requiring a human decision

These are not bugs. They are exactly what PRD §15 calls them: decisions made in the absence of information, carried deliberately, that this build cannot resolve on its own.

**Regulatory / legal (§15.3):**
- **B11 — Personal Care's prohibited-product list (skin lightening, prescription-strength actives) is drawn from general regulatory caution, not sourced from NAFDAC's actual current position.** This category carries real health and legal exposure in Nigeria. The PRD's own text is explicit: *"The list should be reviewed against NAFDAC's actual position rather than accepted from this document."* No amount of engineering closes this — it needs a real regulatory review by someone qualified to do one, before this category goes live with real sellers.
- **B10 — Beauty's hygiene-sensitive subcategory list (lip/eye/liquid foundation) is asserted from general practice, not domain expertise.** The PRD names a specific person whose judgment should override it: *"Eniola's industry knowledge on this is better than mine and should override it."*
- **B12 — Gadgets' 5kg/50cm and Home Goods' 10kg/60cm size boundaries are invented proxies for standard courier limits, not sourced from whichever courier sellers will actually use.**

**Live third-party integrations, unverified end-to-end in this environment:**
- **PostHog:** every event fires correctly with the correct payload (proven exhaustively); nothing has been observed in a real PostHog dashboard, since no real project key is configured here. DoD item 18, Known Issue #44.
- **Resend:** every email sender resolves the correct recipient/subject/content (proven exhaustively, including that contact details never leak into a pre-paid template); no real email has been delivered, since no real API key/verified sending domain is configured here. Known Issue #44.
- **Paystack refunds:** the refund API call is real, correctly sequenced (called *before* any DB state changes, so a click can never claim "refunded" without money moving), and its request-acceptance path is proven; real settlement has not been observed, the same class of gap as the already-known issue #27 (no live completed hosted payment observed either, for the same "needs a tunnel or a real deployment" reason).

**Performance:**
- **Listing-detail Lighthouse LCP measured 2.9–3.3s in this session, over the 2.5s target**, with reasonable evidence (documented CPU contention) that this specific sandboxed environment is a material confound. Needs re-measurement on an uncontended machine or a real Vercel preview before being treated as a confirmed product defect requiring a code fix.

**Deliberate, previously-flagged product gaps (unchanged by this session, still open):**
- No `unsuspendListing`/`reinstateSeller` action exists (Known Issue #35) — a wrongly suspended listing or seller has no undo path short of a raw database write. Same "absence is deliberate" posture the PRD itself states for `updateRating`/`deleteRating`, but worth explicit product sign-off before Epic E is relied on in anger.
- `suspendSeller` does not cascade to the seller's existing listings (Known Issue #36).
- Two metric-precision gaps that are schema/instrumentation-limited, not oversights: leakage signal rate undercounts admin-sourced flags (#40), listing abandonment rate is a DB-derived proxy rather than the literal event ratio (#41 — now technically closeable since real events exist as of Prompt 22, but not switched over).
- No `posthog.identify()` call anywhere — client-fired events never merge with a signed-in user's correctly-identified server-fired events (#45); server-fired events carry no `session_id` at all, a real and documented gap rather than a fabricated placeholder (#46).

**Invented thresholds, carried deliberately per §15.4 (unchanged, not this session's to resolve):**
- B17: every number in §3.4/§3.4.1 (20% second-listing-rate kill threshold, 40% target, the 30-listing/10-seller/15%-conversion browsable gate, 5% dispute-rate flag) is invented, pre-committed specifically so post-launch data can't motivate-read its way around them. Worth arguing with **now**, per the PRD's own words, not after real data exists.

- B3: the 10/50/unlimited listing-limit tiers are invented; watch `listing_limit_reached` against real seller quality once real sellers exist.
