## 1. What this product is

A peer-to-peer recommerce marketplace for Nigeria (beauty-first, multi-category from day one). Sellers list pre-owned goods, buyers pay through escrow-lite (Paystack), funds release on delivery confirmation, platform takes 10% commission. No chat, no negotiation, no auction — the whole product bet is that a seller's *second listing* is the thing to optimize for (primary success metric: **second listing rate within 30 days**, target ≥40%, kill threshold <20% at 8 weeks/50 sellers).

Twenty-one "prompts" (build sessions) have shipped so far, each logged in full in `docs/HANDOFF.md`, plus three un-numbered sessions: one between Prompts 8 and 9 that fixed a critical schema-access bug (§3 below), one after Prompt 11 that ran a full real-browser QA pass over the buyer-facing surface (§3.5), and one after Prompt 15 that walked the entire purchase journey through a real browser and fixed two bugs it found (§3.6). This document summarizes where that leaves the codebase.

**What "live-verified" actually means, concretely:**

- `assign_seller_listing_index`, `increment_completed_sales_count`, `recompute_seller_rating`, `increment_dispute_upheld_count` all fire correctly under real inserts/updates — including, for the rating trigger, from an actual `authenticated`-role session (not just the `postgres` superuser), which is the real test of its `SECURITY DEFINER` boundary (Known Issue #16, now resolved).
- `database.types.ts` was diffed against a real `supabase gen types` run and found to match the hand-authored version field-for-field (two harmless differences: view nullability, `Relationships` completeness) — then, in Prompt 10, **actually swapped to the genuine CLI-generated file**, since `search_listings`'s RPC type needed it. Known Issues #1/#10 resolved.

**The critical bug this live-verification found and fixed:** no migration had ever issued table-level `GRANT`s to `anon`/`authenticated`/`service_role`. RLS policies were all correctly written, but Postgres checks table-level grants *before* evaluating RLS — so every base table returned "permission denied" for every role, including `service_role` (its `BYPASSRLS` attribute bypasses RLS policies, not table grants — a distinct mechanism). This was invisible until Docker made live testing possible; `docs/DECISIONS.md` #18 had flagged the risk and left it conditional on exactly this kind of verification. Root cause: tables are owned by `postgres` (the role migrations run as), and Supabase's own Postgres bootstrap only auto-grants full CRUD to `anon`/`authenticated`/`service_role` for tables owned by `supabase_admin`, not `postgres` — confirmed by reading the Postgres image's own bootstrap SQL directly, not by inspection alone. `20260729055455_grant_table_privileges.sql` grants exactly what each table's RLS policies already expect to enforce, scoped per PRD §7.2's access model. Re-verified end to end afterward: a real authenticated buyer session can insert a rating and the `SECURITY DEFINER` trigger correctly updates the seller's profile.

## 3.8 Payout queue live verification (Prompt 20)

The single thing this prompt most needed to prove, live rather than by inspection, was the double-payout guard — a HARD RULE phrased with a deliberate "non-failed" carve-out (Decision #91) that only makes sense under a specific, non-obvious schema design (a partial unique index, failed rows kept as permanent history, retries as fresh rows). A 21-check `tsx` script (full log in `docs/HANDOFF.md`'s Prompt 20 entry) walked the guard through all three states it needs to handle correctly: a second `queued` row for an already-queued order rejected, a retry row for a since-`failed` order accepted, and a third non-failed row for that same order rejected again. The same script also confirmed, directly rather than by reading the migration, that marking a payout paid leaves the constituent order's own `status` genuinely untouched — the concrete proof behind Decision #89's citation-drift resolution (no `paid_out` order status exists or was invented).

## 4. Key architectural decisions (see `docs/DECISIONS.md` for full reasoning)

- **Column-vs-JSONB split:** shared fields (`price_kobo`, `condition`, etc.) are real columns; category-local fields live in a Zod-validated `attributes` JSONB column. `condition` is modeled *inside* each category's Zod schema, then destructured back out before persisting (Decision #9).
- **Public-column-privacy pattern:** a table with RLS that can't express "hide column X but keep column Y public" gets a dedicated `_public` view instead. Applied to `profiles`, `ratings`, and now `orders` (`orders_participant_view`, Prompt 15, Decision #62 — closes Known Issue #14, verified live from every angle: seller pre/post `paid`, buyer always, anon denied outright).
- **`seller_listing_index`** is assigned by an advisory-lock-serialized Postgres trigger, never application code — now confirmed correct by live execution, not just design.
- **Registry-driven categories:** all 5 category Zod schemas resolve dynamically by slug; no `switch` on category name anywhere.
- **Table GRANTs are not optional even with correct RLS** — Postgres requires both a table-level grant *and* a passing RLS policy; RLS alone is inert without the grant (the reason every future migration must declare GRANTs alongside its RLS policies, in the same migration, going forward).
- **Contact-detail detection (§9.3) is recall-favoring by design**, never a block path: Nigerian phone formats (including letter-substitution and spelled-out digits), email, WhatsApp/Instagram/Telegram, generic URLs. A real bug was caught by its own test battery — an unanchored regex let obfuscation letters bleed into adjacent English words, corrupting detection; fixed with token-boundary assertions (Prompt 9).
- **`browsable` gates the buyer category grid and nav ONLY** (§6.2) — search, "recently listed," and listing detail must never check it. Verified live in Prompt 10 by seeding a non-browsable-category listing and confirming it's absent from the grid but present in search results.
- **Attribute filters on category pages are scoped to `enum`/`boolean` fields only** (Decision #42) — the only types that map to JSONB containment (`@>`), which is what the existing GIN index actually accelerates. Numeric range filters (e.g. battery health %) are out of scope until a different index shape exists.
- **`database.types.ts` is now genuinely CLI-generated** (Decision #43) — never hand-edit it again; regenerate and commit alongside every future migration.
- **Listing-detail attribute rendering is generic and field-name-keyed, never a category-slug switch** (Decision #47) — the two-claims rule (functional_status/cosmetic_grade prominence), remaining-PAO computation, and measurements-as-a-table all key off field names/kinds that recur verbatim across categories, not per-category branches.
- **Admin-only attribute fields (e.g. Gadgets' `imei_last_6`) are stripped at the data-access layer via a registry-declared field list** (`adminOnlyAttributeFields`, Decision #46), not merely skipped at render time — they never enter the RSC payload at all.
- **Public read access on `listings` now covers `status in ('published', 'sold')`, not just `'published'`** (Decision #45) — a real gap Epic C3 AC6 surfaced; every other status (draft/removed/suspended) stays non-public.
- **`orders` has no `authenticated` INSERT/UPDATE policy at all — every write, including initial order creation, goes through the service-role client** (per the table's own migration comment, confirmed live in Prompt 13). Application-level checks (auth, verified email, self-purchase) stand in for RLS on this table, since RLS itself grants nothing to write.
- **`orders.listing_id` uniqueness is a partial index scoped to active statuses, not a blanket column constraint** (Decision #54) — a listing can hold more than one order row over its lifetime (e.g. one `expired`, one later `pending`); code that assumes at most one row per listing (like `hasBlockingOrder`) must query for "any active row," never `.maybeSingle()`.
- **Money is integer kobo everywhere, commission is `Math.floor(amount_kobo * 0.10)` stored as an amount and snapshotted at order creation, never a rate, never recomputed** (§8.3, `computeCommission` in `src/lib/money.ts`) — locked in at the unit-test level (`money.test.ts`, Prompt 13) with a non-round-number case proving the fractional kobo favors the seller.
- **Paystack has no separate webhook-signing secret** (Decision #57) — signatures are verified with the same `PAYSTACK_SECRET_KEY` used for `initialize` calls, confirmed against Paystack's own docs before building anything. `PAYSTACK_WEBHOOK_SECRET` was removed from `.env.local.example`/`README.md`, not left as dead scaffolding.
- **Every Postgres function is `PUBLIC`-executable by default unless explicitly revoked** — a real, load-bearing security fact for this schema (first surfaced as a note in Prompt 10's `search_listings`, made *structurally load-bearing* in Prompt 14's `mark_order_paid`, applied to five more functions in Prompt 15). Any RPC that performs privileged writes not otherwise gated by RLS must carry this same explicit REVOKE/GRANT — never rely on "RLS on the underlying tables will probably block it anyway."
- **Every order state transition is atomic (a single Postgres function, `WHERE status = <expected prior status>`) and audit-recorded in `order_status_transitions`** (Prompt 15, Decision #62) — a table not in PRD §7.1, built because the existing `orders` timestamp columns genuinely cannot disambiguate actor (`delivered_at` is set identically whether the buyer confirmed or the system auto-advanced it) or, for `expired`/`cancelled`, record a timestamp at all. `mark_order_paid` (Prompt 14) was retrofitted to participate too (Decision #65) — the audit trail now covers the entire order lifecycle, not just the transitions Prompt 15 itself introduced.
- **A table-level `GRANT` is not optional even with a correct RLS policy — this bit the project twice, not once.** The original finding (the un-numbered grants-fix session, Prompts 8/9) is a standing note in this document; `order_status_transitions` (Prompt 15) still shipped without its `GRANT SELECT` and was only caught by live verification querying it as a real `authenticated` session (Decision #64). Treat this as a mandatory per-migration checklist item, not a fact to remember once.
- **Image-host validation is one shared module (`src/lib/images/allowed-hosts.ts`), enforced at both the write boundary and every render site, not just one or the other** (Decision #66, post-Prompt-15 QA session) — `next/image` throws synchronously on a non-allowlisted host rather than degrading per image, so a single bad photo URL crashed the entire home page, not just its own card, until this fix. `next.config.ts`, the listing schema's Zod guard, and `ListingCard`/`PhotoGallery`'s render-time checks all derive from the same allowlist now; any future `next/image` usage on listing photos must import the same `isAllowedImageUrl` guard rather than re-deriving its own check.
- **Admin role is a single `profiles.is_admin boolean`, re-verified from the database by every admin server action, never trusted from a session/JWT/middleware decision** (Prompt 19, Decision #79) — `src/lib/admin/require-admin.ts`'s `requireAdmin()` is the one implementation; every future admin action (starting with Prompt 20's payout queue) must call it first, exactly like every existing one does, never re-deriving its own check.
- **The only way to grant admin is `scripts/promote-admin.ts`, run manually with the service-role key** (Decision #80) — there is no server action, UI, or route that can grant admin, and there must never be one (the classic bootstrap problem: the first admin has no existing admin to grant them access). Never wire this into a request handler.
- **RLS is row-level, not column-level — a table with an "owner can update her own row" policy needs a separate `BEFORE UPDATE` trigger (comparing `OLD`/`NEW`) to protect any column that shouldn't be self-editable**, distinguishing a real user session (`auth.uid() is not null`) from the service role (`auth.uid() is null`) (Decision #81, closing a real gap found in `profiles`/`listings` this prompt — `is_admin`/`is_suspended`/`listing_limit_override`/listing suspension state were all directly self-writable before this). Apply the same pattern — extend the existing trigger, don't write a new one — to any future admin-only column added to either table.
- **A HARD RULE's own wording can be the specification for the correct DB design, not just prose to satisfy** (Prompt 20, Decisions #91/#92) — "a single order can never appear in two **non-failed** payouts" only makes sense if failed payout attempts are meant to persist as their own permanent rows (a blanket `UNIQUE` would already make the "non-failed" qualifier redundant). `payouts_order_id_active_unique` — a partial unique index excluding `failed`, the same shape as `orders_listing_id_active_unique` (Decision #54) — is the enforcement; `mark_payout_failed()` creates a fresh, freshly-account-resolved retry row rather than mutating the failing one back to `queued` in place. Read a HARD RULE's exact phrasing this closely before picking a data model, not just its gist.
- **Payout completion is a `payouts`-table-only event — `orders.status` never changes because a payout succeeded or failed** (Prompt 20, Decision #89) — §8.1's order state machine is a closed, exhaustively-diagrammed set with no transition after `released`; the payout's own lifecycle (`queued → paid`/`failed`) is tracked entirely on its own row. Any future admin/payout-adjacent feature must not invent an order-side "paid out" status — there isn't one, and there shouldn't be one.
- **Every success metric is computed directly from the database, not from an event stream, because no queryable event stream exists yet** (Prompt 21, Decision #97) — `track()` has been a `console.log` stub since Prompt 7 and stays one until Prompt 22 consolidates the real PostHog layer. §3.5's own "derived, not emitted" precedent for the primary metric was extended to every other §3.2 metric out of necessity, not choice. Revisit each metric's computation once real events exist — some may stay DB-native (arguably more accurate), some may shift to event-sourced.
- **Every "within N days" metric excludes subjects whose full window hasn't elapsed yet from its denominator entirely** (Prompt 21, Decision #100) — a seller/buyer/listing that's simply too recent to have had a fair chance at the outcome is neither a pass nor a miss; counting it as a miss would artificially depress every rate the moment fresh activity happens, exactly backwards for a growing platform. Applied uniformly across `metric_second_listing_rate`, `metric_listing_to_sale_conversion_by_category`, and `metric_buyer_repeat_rate_30d` — any future "rate within N days" metric must follow the same pattern.
